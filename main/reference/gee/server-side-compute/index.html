    Server-side computation#

    Earth Engine is a compute platform, not just an archive: the useful part is usually the graph you build before any pixel is downloaded — masking, band math, joins, temporal reduction. The gee backend does not hide that. This page shows how to reach it through earthlens, where the boundaries are, and how to fall through to raw ee when the backend's knobs run out.

    It also explains the engine= choice, because that is the one setting that decides whether server-side computation is available at all.

    The short version#

    You want Use
    A temporal composite (mean / median / p90 / trend / …) reducer=, temporal_resolution=
    The composite back in memory, not only on disk materialize=True → DownloadResult.data (a Dataset or DatasetCollection)
    Scene selection by metadata (cloud cover, orbit, …) filters=
    A per-image transform — masking, rescaling, dB conversion cloud_mask=
    Anything else Earth Engine can do el.datasource.client — the raw ee module, already authenticated

    Using filters= or cloud_mask= moves the request onto an Earth Engine engine. That is not a limitation to work around; those are the only engines that can run a graph.

    The three engines#

    engine= selects who materialises the pixels for export_via="url". It does not change the AOI, the CRS, or the values you asked for.

    engine="ee" engine="pixels" engine="eedai"
    Path ee.Image.getDownloadURL ee.data.computePixels GDAL's EEDAI driver via pyramids-eo
    Server-side compute Yes — the full Earth Engine graph Yes — the expression is the graph No — it reads stored pixels
    Size cap 32768 px per axis (auto_split=True tiles around it) the same 32768 px per axis, same remedy none; oversize windows stream to disk in tiles
    Round-trip HTTP + zip the GeoTIFF bytes, directly direct read from the asset
    Extra needed [gee] [gee] [gee] and [eedai]
    Temporal composite server-side server-side client-side, per time bucket

    "pixels" is the engine for a request that needs a graph and wants Earth Engine's current extraction API for it: the GeoTIFF bytes come back directly, with no URL to expire and no zip to unpack, from a grid the request states outright. It does not buy a bigger output — the per-axis cap is the same, and auto_split=True is what gets past it on either path. It is never chosen automatically: "auto" keeps preferring the reader and then "ee", so the preference order is a separate, reviewable decision rather than a side effect of adding an engine.

    One sampling difference is worth knowing, and it is deliberate. "pixels" sends an explicit grid, so it sizes on the metre convention — square metres on the ground, shortening longitude by cos(latitude), the same rule the EEDAI reader uses — while "ee" lets Earth Engine read scale in a geographic CRS as a uniform degree-equivalent. Away from the equator the two therefore return different column counts for one AOI at one scale: at 30° N a degree of longitude is about 13% shorter than a degree of latitude. The AOI, the CRS and the values agree (a live e2e compares their elevation distributions on the same SRTM window); the grid does not. Pass crs_transform= when the grid itself has to be identical.

    engine="auto" (the default) picks eedai when the request is a raw read and the extra is installed, otherwise ee. A request is a raw read when all of these hold:

    • export_via="url" — the asynchronous drive / gcs / asset sinks are Earth Engine-only
    • cloud_mask is None
    • filters is empty
    • the dataset is ee_type="image" or "image_collection"
    • crs is EPSG:4326 or a metre-based projected CRS (a metre scale cannot size anything else)

    So the rule is simply: ask for computation and you get the Earth Engine engine. engine="eedai" raises rather than silently dropping your mask or filters.

    When a collection goes back to Earth Engine anyway#

    Even an eligible collection is sized before the reader serves it, because the reader downloads every scene in the bucket and holds them in memory to reduce. It hands the bucket back to Earth Engine when:

    • the bucket holds more scenes than the scene cap (currently 500)
    • the scene stack exceeds the single-pass pixel budget (currently 2×10⁸ px)
    • the reducer is mosaic — last-wins in Earth Engine's collection order has no client-side equivalent over a scene stack (it would need per-scene masks the reader does not expose), so mosaic stays on Earth Engine. This is the resolution recorded for that case: mosaic is declined client-side and reimplemented nowhere, not quietly approximated. Every other temporal reducer — mean / median / min / max / mode / sum, and the percentile (percentile:<q> / p<q>), trend and sens_slope reducers — is computed client-side by pyramids' reduce_time, so median is a true per-pixel median and a percentile or trend no longer forces the bucket back to Earth Engine
    • the reducer is a named-algorithm composite — LandsatComposite / Sentinel2Composite wrap ee.Algorithms.Landsat.simpleComposite / ee.Algorithms.Sentinel2.CDI, which exist only server-side, so there is nothing client-side to approximate them with and the bucket runs on Earth Engine

    Narrow the window, shorten temporal_resolution, add a property_filter, or use a coarser scale to get back under the budget. These thresholds are internal constants, not public API — treat them as current behaviour rather than a contract.

    Client-side reduction needs pyramids-core >= 0.70.0, and the live EEDAI path has a known gap

    The client-side composite — the true per-pixel median, and the percentile / trend / sens_slope reducers — runs through pyramids' DatasetCollection.reduce_time, whose median / percentile / linear_trend / sens_slope operations ship in pyramids-core >= 0.70.0 (the distribution formerly published as pyramids-gis; the import name stays pyramids). Below that version these reductions are unavailable. The no-nodata caveat carries into them: the EEDAI driver declares no fill, so a statistical reducer folds a scene's fill pixels into the result where Earth Engine would have masked them — the two agree only where the scenes carry no fill over the AOI.

    Known limitation — live EEDAI reduction. pyramids_eo.collection_from_earthengine currently returns an in-memory (datasets=-backed) DatasetCollection, which reduce_time cannot consume — it reads a file- or zarr-backed collection — so a live engine="eedai" collection composite (even median) raises a RuntimeError today. The earthlens wiring is correct, and the reduction is verified against numpy on a file-backed stack; it will work end to end once that upstream reader gap is closed. Until then, pass engine="ee" for a collection composite.

    The two engines are not byte-identical#

    Worth knowing before you compare outputs:

    • Grid. Earth Engine reads scale in a geographic CRS as a uniform degree-equivalent; the EEDAI grid is sized for square metres on the ground. Away from the equator the column counts differ.
    • Resampling. The reader warps from the asset's native resolution locally (nearest by default) where Earth Engine aggregates server-side. For continuous fields read coarser than native — elevation, temperature, reflectance — resample="average" is much closer to Earth Engine; keep nearest for categorical data such as land cover.
    • Nodata in a composite. The EEDAI driver declares no fill value, so the reader's mean / median / min / max / sum run unmasked and fold a scene's fill pixels into the result where Earth Engine would have masked them. They agree wherever the scenes carry no fill over the AOI. When you need Earth Engine's masking exactly, pass engine="ee".

    The AOI, the CRS and the values agree. The sampling does not.

    Level 1 — declarative knobs, no ee code#

    Several Earth Engine operations are plain constructor arguments. Nothing here needs you to import ee.

    Argument Server-side operation
    reducer= temporal reduction: mean, median, min, max, mode, mosaic, sum, a percentile (percentile:<q> / p<q>), trend, sens_slope
    temporal_resolution= raw / daily / monthly / yearly bucketing; each bucket is reduced independently
    variables= select(bands)
    scale=, crs=, resample= resampling and reprojection
    region= a GeoDataFrame cutline — clipped precisely, superseding the bbox
    property_filter= scene-metadata filter string (EEDAI path only, see below)

    A monthly median composite over a polygon, entirely declarative:

    from earthlens.core import EarthLens

el = EarthLens(
    data_source="gee",
    dataset="COPERNICUS/S2_SR_HARMONIZED",
    variables=["B4", "B3", "B2"],
    start="2024-05-01",
    end="2024-08-31",
    lat_lim=[29.9, 30.1],
    lon_lim=[31.2, 31.4],
    temporal_resolution="monthly",
    reducer="median",
    scale=10,
    path="out",
).authenticate(service_account=SERVICE_ACCOUNT, service_key=SERVICE_KEY)

paths = el.download()

    The catalog also encodes reduction advice you inherit for free. COPERNICUS/S1_GRD declares default_reducer: median precisely because backscatter is in dB and averaging dB is not averaging power — so omitting reducer= on Sentinel-1 gives you the defensible choice, not an arithmetic mistake.

    Named-algorithm composites#

    reducer= also accepts a TemporalReducer instance — Percentile(q=90) works — and that is how Earth Engine's named-algorithm composites plug in, since they carry config no string can spell:

    from earthlens.gee import LandsatComposite, Sentinel2Composite

reducer=LandsatComposite(percentile=50, cloud_score_range=10, max_depth=40, as_float=True)
reducer=Sentinel2Composite(threshold=-0.5, reducer="median")
    • LandsatComposite runs ee.Algorithms.Landsat.simpleComposite over each time bucket: a cloud-screened, TOA-calibrated mosaic in one server call. It needs the raw Level-1 collection — the curated LANDSAT/LC08/C02/T1 catalog row is the example — not the T1_L2 surface-reflectance product, because the algorithm performs its own TOA calibration.
    • Sentinel2Composite maps the Sentinel2Cdi mask (ee.Algorithms.Sentinel2.CDI, the parallax-based cloud discriminator) over every scene, then reduces the masked stack with its inner reducer (median by default). The standalone Sentinel2Cdi(threshold=...) mask is also an ordinary cloud_mask= drop-in.

    CDI needs the TOA product, and L2A fails silently

    ee.Algorithms.Sentinel2.CDI is a parallax computation over the TOA band geometry, so it is only valid on COPERNICUS/S2_HARMONIZED (or the legacy COPERNICUS/S2). Pointed at surface reflectance it does not raise: checked live against earthengine-api 1.7.35 with evaluation forced, CDI returns a value on an L2A scene (-0.083) just as it does on the matching TOA scene (-0.075), and the masked band resolves to a pixel. There is therefore no server-side error to rely on — only a mask that is quietly wrong.

    Because the asset id is known at construction, earthlens refuses the pairing itself: a Sentinel2Cdi on cloud_mask= (directly or inside a MaskChain), a reducer=Sentinel2Composite(), or a preprocess: recipe resolving sentinel2_cdi under preprocess=True, against COPERNICUS/S2_SR_HARMONIZED / COPERNICUS/S2_SR, raises a ValueError from GEE(...). The check runs twice — on the arguments before the catalog parse, and again on the ops the flags resolve — so the catalog-driven route is covered by the same refusal, not only the user-driven one. On surface reflectance use Sentinel2SclMask, Sentinel2Qa60Mask or CloudScorePlus.

    Both are validated at construction like every reducer (GEE(reducer=...) resolves instances through the same temporal_reducer_for seam the strings use), are deliberately not in the REDUCERS registry, and exist only server-side: the EEDAI reader declines them (see the collection routing above), so the request runs on an Earth Engine engine.

    property_filter is not filters

    property_filter="CLOUDY_PIXEL_PERCENTAGE < 20" is an OGR attribute-filter string consumed by the EEDAI reader, so it narrows scene selection without forcing the Earth Engine engine. filters= are Earth Engine closures with no string form, which is why the two cannot be the same knob. property_filter is ignored (with a warning) for a single image or an Earth Engine-served request.

    Level 2 — filters=, collection-level compute#

    filters takes an iterable of Callable[[ee.ImageCollection], ee.ImageCollection], composed left to right. Anything you can do to a collection belongs here: metadata filters, .sort, .limit, joins, your own .map.

    earthlens.gee.filters ships the common ones — by_year, by_bounds, by_property_in, by_cloud_cover_lte, by_year_and_bounds:

    import ee

from earthlens.gee import filters

el = EarthLens(
    data_source="gee",
    dataset="COPERNICUS/S2_SR_HARMONIZED",
    variables=["B8", "B4"],
    start="2024-05-01",
    end="2024-09-01",
    lat_lim=[29.9, 30.1],
    lon_lim=[31.2, 31.4],
    reducer="median",
    filters=[
        lambda c: filters.by_cloud_cover_lte(c, 20, property_name="CLOUDY_PIXEL_PERCENTAGE"),
        lambda c: c.filter(ee.Filter.eq("SENSING_ORBIT_NUMBER", 79)),
    ],
    path="out",
)

    by_cloud_cover_lte defaults to Landsat's CLOUD_COVER, so Sentinel-2 needs property_name="CLOUDY_PIXEL_PERCENTAGE" passed explicitly.

    Each of these also exists as a frozen callable class — ByYear, ByBounds, ByPropertyIn, ByCloudCoverLte, ByYearAndBounds, under the earthlens.gee.filters.CollectionFilter base — whose instances carry validated config and are drop-ins for a filters= entry, so the first lambda above can lose its wrapper:

    from earthlens.gee.filters import ByCloudCoverLte

filters=[ByCloudCoverLte(max_pct=20, property_name="CLOUDY_PIXEL_PERCENTAGE")]

    A typo'd keyword or an out-of-range max_pct is refused at construction (frozen=True, extra="forbid"), where a functools.partial would bind the misspelling silently. One naming note: the top-level earthlens.gee.CollectionFilter stays the Callable type alias describing the hook; the class of the same name in earthlens.gee.filters is the base that implements it. Class or function, any filter moves the request onto an Earth Engine engine, as above.

    The expanded filter library#

    Six further class-only selectors cover what SAR, multi-sensor and seasonal work needs — each a frozen, construction-validated CollectionFilter drop-in for a filters= entry (and, like every filter, an Earth Engine-engine request):

    • ByOrbit(pass_direction=..., relative_orbit=...) — pins a Sentinel-1 pass direction (orbitProperties_pass) and/or relative orbit (relativeOrbitNumber_start). Ascending and descending passes have different look geometries, so mixing them in a composite is almost always wrong; at least one constraint is required.
    • BySensor(values=("LANDSAT_8", "LANDSAT_9")) — platform selection via ee.Filter.inList; the default property matches Landsat C2 (SPACECRAFT_ID), Sentinel-2 passes property_name="SPACECRAFT_NAME".
    • ByQuality(property_name=..., op="lte", value=...) — the generic metadata-threshold escape hatch, dispatching to ee.Filter.{lte,gte,lt,gt,eq}, so a new threshold needs no bespoke class. value takes a number, or a string with op="eq" (property_name="SPACECRAFT_ID", value="LANDSAT_8") — a string with an ordering comparison is refused at construction, since Earth Engine orders numbers.
    • BySeason(season="JJA") — one meteorological season (DJF / MAM / JJA / SON) across every year in the date window, expanded to an ee.Filter.Or over its months — the same idiom Climatology uses, so DJF wraps the year boundary correctly.
    • ByMonth(start_month=6, end_month=8) / ByDayOfYear(start_day=152, end_day=243) — calendar windows across every year via ee.Filter.calendarRange; a start after the end wraps (Earth Engine semantics), and omitting the end selects the single period.
    from earthlens.gee.filters import ByOrbit, BySeason

filters=[ByOrbit(pass_direction="ASCENDING", relative_orbit=87), BySeason(season="JJA")]

    Level 3 — cloud_mask=, per-image compute#

    cloud_mask is typed Callable[[ee.Image], ee.Image] and is .map-applied to every image in the collection. Despite the name it is a general per-image hook, not only a mask — any ee.Image expression is fair game.

    earthlens.gee.cloud_masks provides two ready-made masks:

    • sentinel2_scl(image) — Sentinel-2 L2A, dropping SCL cloud shadow (3), cloud medium/high probability (8 / 9) and thin cirrus (10). It deliberately keeps saturated/defective (1) and snow/ice (11).
    • landsat_sr(image, sensor=...) — Landsat C2-L2, keeping the QA_PIXEL Clear bit (bit 6).
    from earthlens.gee.cloud_masks import sentinel2_scl

el = EarthLens(
    data_source="gee",
    dataset="COPERNICUS/S2_SR_HARMONIZED",
    variables=["B4", "B3", "B2"],
    start="2024-05-01",
    end="2024-06-15",
    lat_lim=[29.9, 30.1],
    lon_lim=[31.2, 31.4],
    reducer="median",
    cloud_mask=sentinel2_scl,
    path="out",
)

    Both masks also ship as frozen callable classes — LandsatSrMask(sensor=...) and Sentinel2SclMask(masked_classes=...), under the earthlens.gee.cloud_masks.ImageMask base — validated at construction and drop-ins for cloud_mask=:

    from earthlens.gee.cloud_masks import Sentinel2SclMask

cloud_mask=Sentinel2SclMask(masked_classes=(3, 8, 9, 10, 11))   # also drop snow/ice

    The masks derive their output with updateMask, which keeps image properties — system:time_start in particular — so the per-bucket date filter the composite engine applies after the mask still sees every scene. Like the function forms, an instance on cloud_mask= forces the request onto an Earth Engine engine (the EEDAI reader cannot run a graph).

    The expanded mask library#

    Three further ImageMask classes broaden coverage across the catalog's optical datasets. Each reads a quality band its target dataset declares in the curated catalog, derives its output with updateMask (properties survive), and — like every cloud_mask= — moves the request onto an Earth Engine engine:

    • Sentinel2Qa60Mask() — the standard pre-Scene-Classification recipe: masks the QA60 opaque-cloud bit (10) and cirrus bit (11). Use it for TOA scenes (COPERNICUS/S2_HARMONIZED), which carry QA60 but no SCL band.
    • LandsatQaRefinedMask(sensor=..., max_cloud_confidence=2, max_shadow_confidence=2) — the per-sensor refinement the sensor argument was reserved for: thresholds the QA_PIXEL Cloud Confidence (bits 8-9) and Cloud Shadow Confidence (bits 10-11) fields instead of trusting the single derived Clear bit. Ceilings are 0 (not set) to 3 (high), validated at construction.
    • ModisState1kmMask() — the daily MODIS surface-reflectance products (MODIS/061/MOD09GA / MYD09GA): keeps only pixels whose 2-bit cloud-state field (bits 0-1 of state_1km) reads "clear" (0).

    On a dataset that does not carry the mask's quality band, Earth Engine fails at graph-compute time — the same contract as the first gotcha below; the curated rows named above all declare theirs.

    CloudScorePlus — the state-of-the-art Sentinel-2 mask#

    CloudScorePlus masks a Sentinel-2 scene with Google's Cloud Score+ dataset (GOOGLE/CLOUD_SCORE_PLUS/V1/S2_HARMONIZED). The scores live in a separate collection aligned to the harmonized S2 archive, so the mask links each scene to its score image with linkCollection — a per-image match on system:index — then keeps pixels scoring at or above threshold. Because the link is per image, it works unchanged under collection.map(...) and is an ordinary cloud_mask= drop-in:

    from earthlens.gee.cloud_masks import CloudScorePlus

cloud_mask=CloudScorePlus()                          # band="cs", threshold=0.6 — Google's recipe
cloud_mask=CloudScorePlus(band="cs_cdf", threshold=0.5)

    The two score bands differ: cs scores each pixel on its own; cs_cdf integrates a cumulative distribution and tends to be more conservative over bright surfaces. The threshold is a [0, 1] quality score (not a percentage) and is validated at construction. Cloud Score+ folds shadow signal into both bands, so no separate shadow projection is applied. Reading the second collection is server-side compute, so this mask — like every cloud_mask= — runs on an Earth Engine engine, never the EEDAI reader.

    Ordering, and why it matters#

    The chain is:

    filterDate → filterBounds → filters (left to right) → cloud_mask (.map) → select(bands)

    cloud_mask runs before select on purpose: an optical mask reads a quality band (QA_PIXEL, SCL) that your variables usually omit, so selecting first would strip the band the mask needs.

    The one real constraint: band names must be in the catalog#

    Every requested band is validated against the catalog before the graph is built, so a band your hook creates cannot be requested:

    >>> from earthlens.gee import Catalog
>>> Catalog().get_dataset("COPERNICUS/S2_SR_HARMONIZED").get_band("NDVI")
Traceback (most recent call last):
    ...
ValueError: 'NDVI' is not a band of 'COPERNICUS/S2_SR_HARMONIZED'. Known bands: [...]

    So cloud_mask is the right seam for transforming bands that already exist — masking, rescaling to physical units, dB conversion, a per-image correction — and the wrong seam for adding a new named output.

    If you want a computed index written to disk, pick one of:

    1. Overwrite a declared band. Works today, at the cost of an honest name:

      def ndvi_into_b8(image):
    nd = image.normalizedDifference(["B8", "B4"]).rename("B8")
    return image.addBands(nd, overwrite=True)

      Request variables=["B8"] and the file carries NDVI under the name B8. The catalog's min / max / scale metadata for B8 no longer describes the contents, so this is a deliberate trade, not a recommendation.

    2. Drive ee yourself via the escape hatch below — the clean route for genuinely new outputs.

    3. Compute it downstream from the downloaded bands with pyramids/NumPy, which keeps the archive request and the derived product separate.

    Raw DN to physical units: BandScaler#

    Values arrive as raw digital numbers by default. The catalog records each band's scale (and offset) as metadata — Band.scale is documented as "multiply the raw DN by this to get physical units" — and BandScaler is what applies it, server-side, before the composite, so the temporal reduction happens in physical units:

    el = EarthLens(
    data_source="gee",
    dataset="COPERNICUS/S2_SR_HARMONIZED",
    variables=["B4", "B3", "B2"],
    start="2024-05-01", end="2024-06-15", reducer="median",
    scaled=True,
)

    scaled=True is resolved inside the backend, which already knows the asset id and the requested bands, so neither is restated and the two cannot drift from dataset= / variables=. The default is False on purpose: switching it on would change every existing request's pixel values and dtype at once.

    The explicit form stays public for the cases the flag does not cover — a hand-picked factor set, or a row you want to scale against a catalog you loaded yourself:

    from earthlens.gee.catalog import Catalog
from earthlens.gee.cloud_masks import BandScaler, Sentinel2SclMask

row = Catalog().get_dataset("COPERNICUS/S2_SR_HARMONIZED")
cloud_mask = Sentinel2SclMask() >> BandScaler.for_dataset(row, ["B4", "B3", "B2"])

    The explicit form restates two arguments; keep them in step

    BandScaler.for_dataset(row, bands) duplicates dataset= and variables=, and getting either wrong used to be silent. Two guards now run at GEE(...) construction:

    • a scaler resolved for a different asset than the request asks for raises — both rows often declare the same band names, so the wrong factors would otherwise be applied without a word;
    • a narrower band list than the request logs a warning naming the bands that stay raw DN, since BandScaler passes an unnamed band through by design and the output raster would mix 0–1 reflectance with 0–10000 integers.

    scaled=True / preprocess=True avoid both by construction, which is the reason to prefer them.

    BandScaler.for_dataset(row, bands) reads the factors off the catalog row and skips the bands that declare neither — a row declaring none at all logs a warning and yields an identity, so a request never quietly returns raw DN when you asked for reflectance. BandScaler(factors=(BandFactor(band="B4", scale=0.0001),)) is the explicit form. Scaling raises the dtype from integer to float; use ExportConfig.dtype if you need a narrower output.

    An identity op costs nothing but the warning. scaled=True on a row with no factors, and preprocess=True on a recipe that is only a PassThrough (Sentinel-1's, which Earth Engine has already corrected), both resolve to something that cannot change a pixel — so the backend drops the op instead of mapping it, and the request keeps the EEDAI fast path rather than being pushed onto Earth Engine for a no-op. An explicit cloud_mask= is never dropped: it is run as given.

    Opt-in is deliberate: switching it on by default would change every existing request's pixel values and dtype at once. preprocess() is the one-argument way to get the mask and the scaler together — see "Analysis-ready pixels in one call".

    Composing: masks chain with >>#

    The backend has a single cloud_mask slot, so a mask and a scaler compose into one MaskChain rather than displacing each other:

    chain = Sentinel2SclMask() >> BandScaler.for_dataset(row)   # mask first, then scale
chain.name                                                  # 'Sentinel2SclMask >> BandScaler'

    A chain is itself an ImageMask, flattens (a >> b >> c is one chain of three), and runs left to right. Order is part of the recipe: the mask must read its raw quality band before the scaler's arithmetic touches the pixels. MaskChain.of(...) takes the elements positionally, flattens an inner chain the same way >> does — both recurse, so a chain built by nesting (MaskChain(masks=(chain, f))) unpacks fully too and len(chain.masks) always counts leaves — and accepts any ee.Image -> ee.Image callable — the plain-function forms (landsat_sr, sentinel2_scl), a functools.partial of one, a lambda or a callable instance, none of which have a >> of their own. chain.name labels every one of those shapes. This is not analysis.OperationChain — that one composes client-side operations over a downloaded pyramids Dataset and cannot build an ee.Image graph.

    Every op in the family preserves the image's properties. That matters because the composite engine applies its per-bucket filterDate after the hook, and the reducers and samplers read system:time_start: an op that dropped it would empty every bucket.

    The updateMask masks do it for free. The two ops that rebuild the image (BandScaler, SpeckleFilter) copy them back with copyProperties(source, source.propertyNames()) — note the explicit property list, since copyProperties skips system:* otherwise. Only one of the two has to: checked live, focalMedian returns an image with no system:time_start, so the copy is load-bearing for SpeckleFilter, while addBands(..., overwrite=True) already keeps the source's properties — which is why Earth Engine's own Landsat applyScaleFactors example never copies them — so for BandScaler the copy is belt-and-braces. One caveat either way: the copy carries system:band_names and system:footprint over verbatim, so an op applied after a select() hands on the pre-select band list.

    Radar: SpeckleFilter#

    SpeckleFilter runs ee.Image.focalMedian on the graph — the server-side counterpart of the client-side analysis.FocalMedian, which can only work on an already-downloaded raster. It is the one genuine Sentinel-1 preprocessing gap: Earth Engine's COPERNICUS/S1_GRD already arrives thermal-noise-removed, radiometrically calibrated and terrain-corrected to dB.

    cloud_mask = preprocess("COPERNICUS/S1_GRD") >> SpeckleFilter(radius=50)

    Analysis-ready pixels in one call#

    "Is Sentinel-2 preprocessing included?" — yes, and this is the one argument that says so:

    el = EarthLens(
    data_source="gee",
    dataset="COPERNICUS/S2_SR_HARMONIZED",
    variables=["B4", "B3", "B2"],
    start="2024-05-01", end="2024-06-15", reducer="median",
    preprocess=True,
)

    preprocess=True reads the dataset's curated recipe and applies the MaskChain it describes: the sensor's recommended mask, then a BandScaler over that row's own scale / offset factors. Mask first, then scale — the mask has to read its raw quality band before any arithmetic touches the pixels. The asset id and the band list come from dataset= / variables=, so the flag restates nothing. A dataset with no curated recipe raises at construction rather than quietly doing nothing, and scaled=True beside it is refused: the recipe already scales, so the pair would scale twice.

    The underlying function stays public, for a recipe you want to inspect, extend or hand around:

    from earthlens.gee import preprocess

chain = preprocess("COPERNICUS/S2_SR_HARMONIZED", ["B4", "B3", "B2"])
chain.name                                   # 'Sentinel2SclMask >> BandScaler'
cloud_mask = chain >> SpeckleFilter()        # extend it

    The same two construction-time guards as BandScaler.for_dataset apply when such a chain is handed to cloud_mask= — a mismatched asset id raises, a narrower band list warns — because the explicit form restates arguments the request already carries.

    Composing a flag with your own mask#

    The flags and cloud_mask= are not alternatives: both end up on the backend's one per-image hook, so they are chained rather than displacing each other. The explicit op runs first, verbatim, and the flag's op follows it:

    EarthLens(..., preprocess=True, cloud_mask=CloudScorePlus())
# the op mapped over the stack is:
# CloudScorePlus >> Sentinel2SclMask >> BandScaler

    Both screens apply and neither is dropped; with scaled=True the chain is simply <your mask> >> BandScaler.

    What is guaranteed is the ordering inside the flag's own op — the recipe's mask reads its raw quality band before the recipe's BandScaler touches the pixels. The composition does not extend that across the two: your op is run as given, so arithmetic inside it runs before the flag's mask. The one pairing where that would corrupt pixels is refused at construction:

    EarthLens(..., scaled=True, cloud_mask=BandScaler.for_dataset(row, ["B4"]))
# ValueError: cloud_mask= already carries a BandScaler, and scaled=True resolves
# another one for ['COPERNICUS/S2_SR_HARMONIZED']. ... they would scale the
# pixels twice. Drop scaled=, or drop the BandScaler from cloud_mask=.

    The same refusal covers preprocess=True beside cloud_mask=preprocess(...), and finds the scaler however the explicit chain was grouped. A scaler that resolved to an identity (a row declaring no scale / offset) is exempt on either side: it has no arithmetic to duplicate.

    The recipe is catalog data, not an if/elif over asset ids. It is a preprocess: block on the curated dataset row, typed as earthlens.gee.Preprocess:

    # libs/providers/imagery/src/earthlens/gee/catalog/optical-multispectral.yaml
datasets:                                 # every row nests under this key
  COPERNICUS/S2_SR_HARMONIZED:
    title: "Harmonized Sentinel-2 MSI ... Level-2A (Surface Reflectance)"
    preprocess:                           # the recipe, beside the row's other fields
      mask: sentinel2_scl
      scale: true
      note: >-
        Level-2A arrives as 0-10000 scaled surface reflectance; the SCL band
        carries the scene classification the mask reads.

    Typing it as a declared field is what makes the validation real: Dataset is frozen but does not forbid extra keys, so an undeclared preprocess: block would have been dropped in silence and a typo'd recipe would have read as "this dataset has no recipe". With the field declared, an unknown mask: name or a misspelled key inside the block fails at catalog-load time.

    Shipped recipes:

    Dataset Mask Scale
    COPERNICUS/S2_SR_HARMONIZED sentinel2_scl yes
    COPERNICUS/S2_HARMONIZED (TOA) sentinel2_qa60 yes
    LANDSAT/LC08/C02/T1_L2, LC09, LE07 landsat_sr yes
    MODIS/061/MOD09GA, MYD09GA modis_state_1km yes
    COPERNICUS/S1_GRD — (PassThrough) no

    Two rules keep it honest:

    • A dataset with no recipe raises. preprocess is never a silent no-op; compose your own chain from the cloud_masks library, or curate a recipe onto the row.
    • A recipe with nothing to apply says so. Sentinel-1 is that case — COPERNICUS/S1_GRD already arrives thermal-noise-removed, calibrated and terrain-corrected to dB, so its recipe is an explicit PassThrough and its note (logged when the recipe resolves) names speckle filtering as the one remaining step.

    Because the result is an ordinary MaskChain, you can extend it — preprocess(...) >> SpeckleFilter() — or ignore it and pass your own chain instead. preprocess=True enforces the same two rules: an uncovered dataset raises from GEE(...), and a recipe with nothing to apply still resolves to the explicit PassThrough.

    Level 4 — .client, the full escape hatch#

    When the knobs run out, take the authenticated ee module and do whatever Earth Engine does. You do not re-do authentication; client is a lazy property that returns the initialized module.

    el = EarthLens(
    data_source="gee",
    dataset="COPERNICUS/S1_GRD",
    variables=["VV"],
    start="2024-01-01",
    end="2024-03-01",
    lat_lim=[29.9, 30.1],
    lon_lim=[31.2, 31.4],
    path="out",
).authenticate(service_account=SERVICE_ACCOUNT, service_key=SERVICE_KEY)

gee = el.datasource          # the GEE backend instance
ee = gee.client              # the initialized `ee` module
print(gee.project)           # the resolved Cloud project

s1 = (
    ee.ImageCollection("COPERNICUS/S1_GRD")
    .filterBounds(ee.Geometry.Rectangle([31.2, 29.9, 31.4, 30.1]))
    .filterDate("2024-01-01", "2024-03-01")
    .filter(ee.Filter.eq("instrumentMode", "IW"))
)
speckle_filtered = s1.map(lambda img: img.focal_median(30, "circle", "meters"))
composite = speckle_filtered.select("VV").median()

    From here you have full parity with the Code Editor: ee.Algorithms, reduceRegion(s), ee.Join, ee.Classifier, ee.Reducer combinations, ee.Image.expression, arbitrary .map.

    Getting results back into Python#

    earthlens meets you on the return trip, so you do not hand-roll getInfo() paging:

    Helper Does

    sample_points_to_gdf(...) the same, returned as a GeoDataFrame
    feature_collection_to_gdf(fc) / feature_collection_to_dataframe(fc) download an ee.FeatureCollection
    feature_collections_to_dataframe([...]) the parallel variant over many collections

sampled = sample_points_to_gdf(composite, stations_gdf, scale_m=10, reducer="mean")

    Exporting a graph you built yourself#

    For a computed image too large for getDownloadURL, use the asynchronous sinks. Set wait_for_export=False and download() returns TaskInfo objects at submission time instead of blocking; list_recent_tasks, get_task_status, wait_for_task_id, cancel_task and resolve_destination track them. The batch sinks are Earth Engine-only, so engine= is ignored there.

    Exporting a video#

    A collection you built through .client can also leave as a video: VideoSink queues an ee.ImageCollection of frames through ee.batch.Export.video.toDrive / toCloudStorage — the only two video targets Earth Engine offers — and returns the same TaskInfo the other batch exports do, with wire task type EXPORT_VIDEO. It is a standalone frozen model like TableSink (the image-shaped Sink ABC does not fit a frames export), validated at construction: a gcs sink without its bucket is refused up front, fps must be in Earth Engine's [0.1, 120], and dimensions is a positive max dimension or "WIDTHxHEIGHT". A Drive export with no folder lands in the Drive root. Every frame must be an 8-bit RGB image — visualise first — and the caller provides the collection (nothing in the download pipeline produces frames):

    from earthlens.gee import VideoSink

frames = s2_monthly.map(lambda img: img.visualize(bands=["B4", "B3", "B2"], min=0, max=3000))
info = VideoSink(destination="drive", folder="videos", fps=6, dimensions=720).write(
    frames, prefix="nile_delta_2024", region=aoi
)
info.task_type   # "EXPORT_VIDEO" — track it with get_task_status / wait_for_task_id

    Like every ee.batch export this is Earth Engine-only; the EEDAI reader never applies to an asynchronous export.

    Table exports: BigQuery and FeatureView options#

    TableSink exports an ee.FeatureCollection to any of its five targets (drive / gcs / asset / bigquery / featureview), and the two server-side targets carry their options:

    from earthlens.gee import TableSink

TableSink(destination="bigquery", table="proj.ds.tbl", overwrite=True).write(fc, description="stations")
TableSink(
    destination="featureview",
    asset_id="projects/my-proj/assets/stations_fv",
    ingestion_time_parameters={"maxFeaturesPerTile": 1500, "thinningStrategy": "HIGHER_DENSITY"},
).write(fc, description="stations")
    • overwrite / append — overwrite replaces what is already there, append adds to a table with a compatible schema. Earth Engine refuses both at once, so the sink refuses both at construction. For a BigQuery table the SDK states the consequence of setting neither — "the export fails if the table already exists and both overwrite and append are false" — while for an asset it documents only that overwrite permits replacing one, without stating what happens when it is left off. Their scopes differ, and each is the set of factories whose signature declares the parameter: append is BigQuery's alone, while overwrite is also taken — and forwarded — by asset, since ee.batch.Export.table.toAsset(..., overwrite=…) is a declared option. So re-exporting a table asset in place is expressible:

    TableSink(destination="asset", asset_id="projects/p/assets/stations", overwrite=True)
    - FeatureView serving options — toFeatureView takes a single ingestionTimeParameters dict, and maxFeaturesPerTile, the thinning strategy and friends all go inside it, not as separate kwargs. - Address validation — each destination's required address (bucket for gcs, asset_id for asset / featureview, table for bigquery) is checked at construction, so a misconfigured sink fails at the call that built it instead of as a late server error. drive with no folder is valid: Earth Engine exports to the Drive root. The BigQuery table is checked for shape too — the sink mirrors Earth Engine's own project.dataset.table rule, so table="nodots" raises here rather than as an EEException at write(). - file_format is scoped like the rest — only drive and gcs pass it on to their Export.table.to* factory, so setting it on asset / bigquery / featureview is refused instead of silently ignored, and the value itself is a fixed vocabulary (CSV, GeoJSON, KML, KMZ, SHP, TFRecord) rather than a free string Earth Engine may reject later. The refusal keys off whether it was set, which is why the field defaults to None and not to "CSV": an explicit file_format="CSV" on a table destination is the same mistake as any other format and is refused too. sink.effective_file_format answers what Earth Engine will write — "CSV" for a file destination that set none (its own default), None for a destination that writes no file.

    Whatever the destination, the queued task's wire type — what TaskInfo.task_type carries and what list_recent_tasks(task_type=...) filters on — is EXPORT_FEATURES: BigQuery and FeatureView create the same ee.batch.Task.Type.EXPORT_TABLE tasks the file targets do (the enum name differs from its wire value). Videos are EXPORT_VIDEO, images EXPORT_IMAGE.

    Temporal helpers over a collection#

    Four frozen, validated config objects build a server-side graph over an ee.ImageCollection you hold — the .client collection above, or one you built yourself. They answer the questions a single reducer cannot: when did it change, how does this period compare to normal, which scene is nearest a date, and fill the holes before reducing. Each is imported from earthlens.gee.

    TemporalSegmentation (LandTrendr / Ccdc) finds breakpoints in a per-pixel trajectory — disturbance and recovery — and returns a SegmentationResult wrapping the algorithm's array-valued ee.Image, never a plottable raster. Mask clouds first; the algorithms assume a clean series:

    from earthlens.gee import LandTrendr

nbr = masked_collection.map(lambda img: img.normalizedDifference(["B5", "B7"]).rename("NBR"))
result = LandTrendr(maxSegments=6).segment(nbr)   # invert=True by default for a vegetation index
vertices = result.array                            # the ee.Array image, for your own getInfo/export

    Climatology reduces a collection per calendar period across a baseline (dayofyear / month / season), and anomaly() is the observed-minus-baseline companion:

    from earthlens.gee import Climatology

clim = Climatology(period="month", baseline=(1991, 2020), reducer="mean")
monthly = clim.climatology(collection)                       # one image per month
june_2024 = clim.anomaly(collection, collection_2024, 6)     # this June vs the 1991-2020 June mean

    ClosestImage selects the scene nearest a target date, within an optional tolerance (an out-of-range target with a tolerance set yields an empty selection rather than a distant scene):

    import datetime as dt

from earthlens.gee import ClosestImage

nearest = ClosestImage(target=dt.date(2024, 6, 1), tolerance=dt.timedelta(days=15)).select(collection)

    GapFill fills temporal holes before a reduction or sampling, by linear / nearest / harmonic interpolation over a within-max_gap neighbour join — max_gap is a refusal, not a hint, so a pixel with no valid neighbour in the window stays masked:

    import datetime as dt

from earthlens.gee import GapFill

filled = GapFill(method="linear", max_gap=dt.timedelta(days=30)).fill(collection)

    Joining two collections#

    Earth Engine's five join strategies ship as frozen config objects — InnerJoin, SaveAllJoin, SaveBestJoin, SaveFirstJoin, SimpleJoin, all under the Join base — each exposing the SDK's own apply(primary, secondary, condition) seam. The wrapper names the intent (matches_key, ordering, measure_key) and validates it at construction (frozen=True, extra="forbid"), where the raw factory would bind a typo'd keyword silently; the condition stays an ordinary ee.Filter, exactly as raw Earth Engine spells it. A join is inherently a two-collection operation, so these are standalone composables for .client-level graphs — never drop-ins for the single-collection filters= hook:

    import ee

from earthlens.gee import SaveAllJoin

# Hang each Sentinel-2 scene's cloud-probability image on it, by scene id.
condition = ee.Filter.equals(leftField="system:index", rightField="system:index")
joined = ee.ImageCollection(
    SaveAllJoin(matches_key="probability").apply(s2, s2_cloud_prob, condition)
)

    GapFill builds its within-max_gap before / after neighbour lists through SaveAllJoin with an ee.Filter.And(maxDifference, ...) condition — the same pattern to copy for any temporal-neighbour join. (CloudScorePlus deliberately stays on linkCollection, a per-image system:index link that needs no join plumbing.) Joins are server-side compute: a pipeline using one runs on an Earth Engine engine, never the EEDAI reader.

    Tagging traffic for billing#

    Earth Engine attaches a workload tag to every request it serves, and Cloud billing breaks cost out by it. WorkloadTag is the earthlens scope for one — GEE.workload_tag is the backend convenience that returns it:

    with gee.workload_tag("drought-monitor-2024"):
    paths = gee.download()   # every EE-served request in here carries the tag

    The tag is validated at construction (1-63 characters, lowercase alphanumeric at start and end, - and _ allowed between), so a typo raises immediately rather than mid-download. That is the rule the SDK's validator enforces (ee/_state.py, _WorkloadTag.validate), which is stricter than the one ee.data.setWorkloadTag's own docstring states: the docstring allows mixed case and dots, the validator refuses both — setWorkloadTag("A1") and setWorkloadTag("a.b") each raise ValueError. earthlens follows the validator, so WorkloadTag(tag="A1") fails at construction instead of on entry. Unlike the SDK's own ee.data.workloadTagContext — whose exit calls resetWorkloadTag() and so resets to the default tag — WorkloadTag saves the tag it found on entry and restores exactly that on exit, exception or not, which is what makes nesting work: an inner scope hands back to the enclosing tag instead of wiping it.

    The tag covers the Earth Engine-served calls (getDownloadURL, computePixels, ee.batch exports) — which is where billing accrues. The EEDAI reader fetches stored pixels through GDAL, not ee, so an engine="eedai" read is never attributed; tagging an EEDAI-only run buys nothing.

    Per-process, and not thread-safe

    The tag is process-wide SDK state and the save stack is a plain list, so the scope nests safely within one thread but two threads entering scopes concurrently interleave their saves and can restore each other's tags. Tag a run from the thread that drives it, or give each worker its own process. Exiting a scope that was never entered raises RuntimeError naming the tag, rather than popping an empty stack.

    Managing assets#

    export_via="asset" creates assets; AssetManager is what manages them afterwards — a dedicated control-plane object over the ee.data asset family, deliberately not methods on GEE, so the read-focused backend never grows destructive verbs and the intent is explicit at the call site:

    from earthlens.gee import AssetManager

manager = AssetManager(project="my-project")
manager.create_folder("projects/my-project/assets/runs")
for row in manager.list_assets("projects/my-project/assets/runs"):
    print(row)                      # AssetInfo(projects/my-project/assets/runs/x, IMAGE, 1024)
manager.copy_asset(src, dst)        # overwrite=True to replace
manager.rename(src, dst)
manager.set_acl(dst, {"all_users_can_read": True})
manager.delete(src)                 # destructive, immediate, no undo

    Reads (get_asset, list_assets, the create calls) come back as frozen AssetInfo rows that print as one line each. Ingestion (start_ingestion / start_table_ingestion, a gs:// manifest in, an asset out) is asynchronous like the batch sinks and returns the same TaskInfo, so get_task_status / wait_for_task_id / cancel_task work on it unchanged. Asset management is pure control-plane: it is server-side regardless of any request's engine=, and the EEDAI reader is never involved.

    Pushing a local classifier server-side#

    A tree model trained locally — Epic 2's client-side Classify, or any fitted scikit-learn DecisionTreeClassifier / RandomForestClassifier — can classify an arbitrarily large image server-side without retraining and without uploading the training data. ClassifierCodec encodes the fitted trees into the text format ee.Classifier.decisionTree / decisionTreeEnsemble accept (a pure-Python port of geemap's tree-string bridge; geemap is not a dependency):

    from earthlens.gee import ClassifierCodec

codec = ClassifierCodec(feature_names=("B4", "B8"))   # band name per feature column, in order
classifier = codec.to_ee(model)                       # ee.Classifier.decisionTreeEnsemble(...)
labelled = image.classify(classifier)                 # server-side, over any image

    Classify trains on band indices while Earth Engine classifies by band name, so ClassifierCodec.for_classify(operation, {0: "B4", 1: "B8"}) builds the codec from the operation's own training bands, and the public Classify.estimator accessor hands over the fitted forest: codec.to_ee(operation.estimator). The classify graph is server-side compute, so the request is Earth Engine-only (engine="ee"); the client-side Classify itself runs after a download and affects no engine choice.

    An ensemble votes differently server-side

    The encoding is exact — every split threshold and leaf label survives the round trip — but the aggregation is not the same rule. ee.Classifier.decisionTreeEnsemble takes a hard majority vote over the member trees; RandomForestClassifier.predict takes the argmax of the averaged predict_proba. The two agree whenever the trees are unanimous, and exactly for a single DecisionTreeClassifier (there is no vote to take), but they can disagree the moment the members split. A pixel whose three trees vote [3, 9, 9] is labelled 9 server-side even when the forest's averaged probabilities favour 3.

    So spot-checking a few pixels of the server-side result against model.predict will show mismatches on a non-unanimous forest, and they are this rule rather than a faulty export. To compare like-for-like, run codec.from_ee(classifier) — the TreeEnsemble it returns applies Earth Engine's vote, tie-break included. Earth Engine documents the majority vote but not how it settles a tie, which an even number of members produces routinely, so that half was checked live against ee.Classifier.decisionTreeEnsemble (earthengine-api 1.7.35): it returns the smallest tied label — [1, 2] → 1, [3, 9] → 3, [0, 4] → 0, [5, 5, 8, 8] → 5 — regardless of the order the trees are given in, which is what TreeEnsemble does. test_ml_e2e.py (marker e2e) re-runs that comparison against the live service. If you need the forest's exact labels, classify locally after a download with Epic 2's Classify.

    from_ee is the partial reverse: it parses the tree strings back into a TreeEnsemble, a pure-Python hard-majority-vote predictor — not a scikit-learn estimator, since the fitted probabilities do not survive the string format. It reads the strings off a classifier built client-side; one trained server-side keeps its trees on the server, so fetch them first (classifier.explain().getInfo()) and pass the strings.

    Choosing an engine, in practice#

    Situation Engine
    Any cloud_mask / scaled= / preprocess= / filters / computed graph ee (forced)
    A computed graph and an AOI over 32768 px ee or pixels, either with auto_split=True, or drive
    An output grid that must align with an earlier download ee or pixels with crs_transform=
    Raw pixels from one asset, large AOI eedai — no 32768-px cap, no zip round-trip
    A composite whose masking must match Earth Engine exactly ee
    Long time series over a small AOI eedai, watching the scene cap
    export_via other than "url" ee (the sinks are Earth Engine-only)
    Not sure leave engine="auto"

    Gotchas#

    • cloud_mask and filters on a static ee_type="image" dataset are applied verbatim. A filter can reject the single wrapped image and empty the collection; a mask reading an absent band fails when the graph is computed. The backend logs a warning but cannot validate it upfront — it surfaces as an opaque Earth Engine error at download time.
    • Mixed-resolution band requests (10 m B4 + 20 m B11 + 60 m B1 in one call) are a sharp edge on the EEDAI path. Request one resolution group at a time, or use engine="ee".
    • cog=True applies to the paths that write the raster themselves — the EEDAI reader and engine="pixels". getDownloadURL and the batch sinks ignore it, and so does resample=, which is the EEDAI reader's warp kernel alone.
    • nodata= is honoured by engine="pixels" on the "url" sink (the expression is unmasked with it and the written raster declares it) and by export_via="drive" / "gcs" (Earth Engine's own GeoTiffImageExportOptions.noData). It is not a field on the pixel API's request — a body carrying one is refused with Unknown name "nodata" at 'grid' — and an asset export has no file format at all, so that sink and getDownloadURL ignore it and warn. Without it, a masked composite's pixels come back as 0 with nothing declared.
    • high_volume= is engine="pixels" only; any other engine warns and initialises against the regular endpoint.
    • auto_split=True applies to engine="ee" and engine="pixels", which share Earth Engine's 32768-px per-axis cap. Measured, because the guide implies otherwise: a computePixels request of 39,479 × 12 px comes back as Pixel grid dimensions (39479x12) must be less than or equal to 32768. The reader has no such cap, so auto_split means nothing to it.
    • Credentials are always needed, even for engine="eedai": the request is built through ee before its pixels are fetched.
    • No Sentinel-1 preprocessing ships in the backend — no speckle filter, no terrain correction. Note that Earth Engine's own COPERNICUS/S1_GRD is already thermal-noise-removed, calibrated and terrain-corrected to dB upstream; speckle filtering is the genuine gap, and belongs in a cloud_mask hook or the escape hatch.
